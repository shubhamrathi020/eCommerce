## Patterns and lessons (fill as they emerge)
- Shell of Windows Git Bash: a large multi-file heredoc can fail to parse; write files with the Write tool instead.
- Angular resources: `resource.value()` throws in error state; guard with `hasValue()`. Errors must be `Error` instances (use `ApiException`) or they are wrapped.
- Signals: never write to a signal inside a `computed` (NG0600); load persisted state in the constructor, not lazily in a computed. Output names must not match native DOM events (`toggle`, `change`...).
- SSR: an Angular Router navigation during SSR becomes a real 302; set `RESPONSE_INIT.status` for 404s. Keep server rendering free of `window`/`matchMedia` (guard, jsdom lacks matchMedia too).
- Route guards: call every `inject()` before the first `await`.
- Header has search forms too: when scripting the browser, scope selectors (e.g. `aside form`) or you may click the wrong submit button.
- Search box tests: drive with real DOM events and wait a few debounce periods; keep `mockLatencyMs: 0`.
- Identity in mocks: `MockUserStore` holds users, session and lockout data; anything that must follow the signed-in owner (cart, orders, addresses) reads `currentUserId()` from it.
- Admin mocks: `MockAdminState` holds an overlay (edits, notes, roles, audit) over seeded data; every admin API calls `state.require(permission)` first and `state.record(...)` on writes.
- When a test looks for a button by attribute (e.g. `aria-pressed`), scope it to the component; pages often have several.
- Never run broad process killers (for example `taskkill /IM node.exe`); stop a dev server by the port it listens on.
- Python patch scripts: write regexes containing `` with `chr(92)` or a raw string, or use the Edit tool; a plain string turns `` into an invisible backspace.
- Anything a spec imports from `@ecom/shared/data-access` must be exported from its index (a missing export shows up as `Cannot convert undefined or null to object` in TestBed.inject).
- Stock: `MockInventoryStore` is the single source of stock in the mocks. Shop reads (catalog, search, cart) call `inventory.apply(products)` for available units; admin calls `apply(products, 'onHand')`. Never write stock into a product; add a ledger movement (`sell`, `restore`, `adjust`, `transfer`) so on hand always equals baseline plus movements.
- Notifications: `MockNotificationStore` is the single source for the bell, preferences, alert subscriptions, templates and the delivery log (one storage key, like the other stores). Any mock API or trigger point that sends a message calls its `deliver(templateKey, to, vars, { userId?, link? })`, never `MockMailbox` directly, so every send is logged and (with a `userId`) reaches the bell.
- Cross-app gap: admin product edits (price, title, etc.) are NOT visible to the shop's own catalog reads in this mock (separate stores, a known limitation). A trigger that depends on an admin edit (e.g. a price-drop alert) must run at the moment the admin saves, not wait for a later shop-side read. Stock is the one exception: `MockInventoryStore` is shared, so admin stock changes ARE seen by the shop.
- Never bind an `NgOptimizedImage`'s `priority` (or any "first render only" hint) to a live array index in a list that can grow without a full replace (e.g. "load more"/infinite scroll). Angular throws if `priority` changes after that image has already been measured. Decide the priority set once, when the list is freshly loaded, and keep it fixed while appending.
- When two independent feature libraries (`type:feature`) need to coordinate UI (e.g. stacking fixed bars so they don't overlap) they cannot import each other — the module boundaries forbid `type:feature` depending on `type:feature`. Put a small shared signal-based service in `shared/core` instead (see `BottomBarService`).
- Never mark something "verified" from reading code alone when an empirical test is possible; a grep proves code isn't there, not that behaviour is correct. `withEventReplay()` alone did **not** make this app's forms safe from an early native submit — only found by actually throttling a real browser and trying it (see BRD 12's FH-06 correction). The fix that actually holds: the submit button is `disabled` starting in the server-rendered HTML itself, not a client script racing to attach in time.
- An RxJS `.subscribe(cb)` callback can fire synchronously, during the `subscribe()` call, before a `const` holding the returned `Subscription` has been assigned; referencing that `const` inside the callback (e.g. to unsubscribe after the first emission) throws "Cannot access before initialization". If you only need the first emission, just don't unsubscribe.
- Docker Desktop Kubernetes: LoadBalancer services normally auto-publish on `localhost`, but if something else on the machine already owns port 80/443 the mapping is silently unusable; verify ingress routes with `kubectl port-forward` and a `Host:` header instead of trusting a browser hit on `*.localtest.me`. Also: Docker Desktop's cluster has no metrics-server by default, so a freshly-applied HPA reads `cpu: <unknown>` until one is installed — expected, not a manifest bug.
- Prisma 7 changed the connection model: no `url` in the schema's `datasource` block any more (validation error), connection details go in a `prisma.config.ts` read by the CLI, and the running app builds its own driver adapter (`@prisma/adapter-pg`) instead of Prisma reading `DATABASE_URL` implicitly. `pnpm exec prisma ...` run through pnpm can execute with the workspace root as cwd even after a shell `cd`, so resolve `.env` with an absolute path (`import.meta.dirname`), not a bare `dotenv/config` import. The generated client also needs `@prisma/client-runtime-utils` as an explicit dependency under pnpm's strict node_modules, and the webpack build needs `"importHelpers": false` in the api's tsconfig or the production image fails on a missing `tslib` (a dev-only dependency of the workspace, absent from the pruned production install).
- A backend module boundary: `apps/api` (`scope:api`) may only import `@ecom/shared/models` (`type:models`), never the Angular-only shared libs — enforced by an eslint depConstraint, the same pattern as the frontend's own boundaries.
- When only part of the real backend exists, add a narrow flag (`AppConfig.realAuth`) rather than overloading `useMocks`: it keeps every untouched module on mocks with zero changes, and a mirror method on the mock user store (`mirrorSession`) keeps the rest of the mock world consistent with whoever the real API says is signed in.
- NestJS uses constructor injection, not Angular's `inject()` function — importing `inject` from `@nestjs/common` (it doesn't exist there) silently breaks TypeScript's inference for that whole file instead of failing loudly at the `inject` call site itself: every field/method touching the broken-typed property cascades into dozens of unrelated "implicitly any" errors elsewhere in the file. When a file suddenly has a wall of unrelated `TS7006` errors, check for one real root-cause type error first (often a wrong import) rather than annotating every symptom.
- A Meilisearch client's `facetDistribution` values are typed `Record<string, number>`, but `x ?? {}` (an untyped empty object literal) as the fallback widens the inferred type of the whole expression to `Record<string, number> | {}`, and `Object.entries()` on that union degrades to `[string, unknown][]`. Fix: cast the fallback (`?? ({} as Record<string, number>)`), not the consumer.
- Threshold-style facets (rating "4 stars & up", discount "25% or more") aren't a single field Meilisearch can facet-count directly; each step needs its own `count()`/`limit:0` query. Categorical facets (brand, a `attr_<key>` array field) use Meilisearch's own `facetDistribution` directly. Getting "this option's count if you added it" (ignoring the option's own currently-applied filter) needs one extra query per *active* filter group, not per facet group — bounded by how many filters are actually selected, not by the catalog's facet count.
- MongoDB's positional `$` operator only has meaning in the **update** document — it can't be referenced inside the **query**/filter (`{ 'variants.$.stock': {...} }` as a filter clause is not valid and just matches nothing, silently). To atomically update one matching array element while checking a condition on that same element, put the condition in `$elemMatch` in the filter (`{ variants: { $elemMatch: { id, stock: { $gte: n } } } }`) and keep the positional `$` only in the `$inc`/`$set` update. Caught this by actually placing a real order, not by reading the code — worth remembering, since the wrong version compiles and type-checks fine and only fails at the exact "insufficient stock" runtime check, for every request.
- Standalone MongoDB (no replica set) does not support multi-document ACID transactions; per-document atomic updates (`findOneAndUpdate`/`updateOne` with a guard condition) are still safe on their own, just not composable into an atomic group without a transaction. A compensating-rollback pattern (undo the ones that already succeeded if a later step fails) is a reasonable, honest substitute for a single order's multiple cart lines, and should be labelled as such rather than implied to be fully ACID.
- A build that works under `nx serve` can still be broken in the production image: the only thing that caught `apps/api/tsconfig.app.json`'s `target: es2021` (it made the bundle move Prisma's class fields ahead of `super()` - "Must call super constructor in derived class" on every database request) was running the *built container* on Kubernetes. Before calling a backend BRD done, run the production image at least once, not just the dev server and the test suite.
- Kubernetes Pod Security `restricted` forbids CHOWN/root even in an init container, so an upstream image whose entrypoint must chown a fresh volume (official Postgres) cannot run there; give that workload its own namespace at `baseline` and say so, rather than weakening the whole namespace. `fsGroup` only changes *group* ownership, never the owning user, so it does not fix this. mongo, redis, rabbitmq and meilisearch did not need the exception. A container-level `capabilities: drop: [ALL]` also strips CHOWN from root - it was the actual last blocker even after the namespace move.
- Kubernetes exec probes default to a 1-second timeout; `rabbitmq-diagnostics` boots its own Erlang node and routinely takes longer, so the pod looked dead (probe failures, restart loop) while its own log said "Server startup complete". Set `timeoutSeconds` explicitly on exec probes for slow CLIs, and add a `startupProbe`.
- Docker Desktop's Kubernetes DOES enforce NetworkPolicy (a Job whose labels weren't in an allow rule hit a hard 30 s Mongo timeout). Don't assume a local CNI ignores them; every one-shot Job needs its `job-name` label in the allow list.
- Re-using an image tag (`shop-api:local`) after a rebuild can run the *old* image in the cluster; the pod's `imageID` shows the stale digest. Tag each build uniquely and compare `imageID` with `docker inspect`. `kubectl set env`/`set image` changes also survive `kubectl apply -k` - remove them explicitly or they become invisible drift.
- Load-testing from one machine measures the rate limiter, not the system: with the defaults, ~70% of browse requests and every flash-sale checkout were 429s. Raise `RATE_LIMIT_*_PER_MIN` for the run, then remove them. A `Secure` cookie (production config) is dropped over plain HTTP, so cookie-dependent scenarios must go through HTTPS.
- On Windows Git Bash, MSYS rewrites leading-slash arguments (`/scripts/x.js` becomes `C:/Program Files/Git/scripts/x.js`); prefix docker/kubectl commands with `MSYS_NO_PATHCONV=1`, and `kubectl exec` paths need `sh -c "..."`. Docker Desktop must be running for the local cluster - its containers and the cluster did not come back on their own after a reboot.
- A hook like `rxResource({ stream: () => inject(Api).list() })` fails: `inject()` inside the stream callback runs outside the injection context and the resource just reports an error, so the page silently shows nothing. Inject into a field first and call the field.
- A test that hard-codes a "future" date is a time bomb: `http-auth.api.spec.ts` had a session expiry of 2026-10-01 and began failing on 2026-10-02 with a baffling `null` instead of a user id. Derive such dates from `Date.now()`.
- Mock orders derive their whole fulfilment progress from the confirmation time (`withProgress`: delivered = confirmed + 6 minutes), ignoring any `delivered` timeline entry you save. To fabricate a delivered order in a test, back-date the confirmation, not the delivery.
- State saved in localStorage by an older build replaces the whole seeded object, so templates or defaults added later never appear for returning users. The notification store now merges missing seed templates on read; do the same for any new seeded record set.
- A "pure engine in the shared models library + optional extras argument" keeps real-backend code unchanged while mocks gain features: `priceCart(stored, products, now, extras = {})` priced identically without extras (there is a test that proves it), so BRD 14 changed no backend behaviour. When extending a function both sides share, add optional inputs and a test that the old call is byte-for-byte unchanged.
- Counting from source records beats keeping counters: flash-deal units sold are summed from live orders, so a cancelled order restores them with no extra code or race. Same for anything derived from orders.
- Heavy jsdom flows (whole mock catalog plus axe) can exceed Vitest's 5-second default when `nx run-many` runs everything in parallel, and fail only then. Use `vi.setConfig({ testTimeout: 30_000 })` at the top of such spec files.
- Zoneless tests: drive test hosts with signals and `await fixture.whenStable()`.
- `@nestjs/throttler`'s `@Throttle()` decorator arguments are evaluated at *module-import time* (confirmed by reading its source in `node_modules`), before `main.ts` ever calls `loadConfig()` — so a decorator argument can structurally never read a runtime/env-configured limit. Any per-route limit that must be configurable needs a custom guard reading config via DI at *request* time instead (see `RateLimitGuard`, BRD 22).
- A new cache-aside layer over an existing write path (BRD 22's catalog cache over BRD 21's `InventoryService` stock decrement) can silently miss an invalidation site: adding the cache to catalog *reads* is not enough if a completely different service (inventory/order writes, not the admin catalog-write path) also mutates the same underlying data. Found only by re-running the full test suite and seeing exact off-by-N stock assertions fail, not by reasoning about the code. When adding a cache over data more than one service can write, grep for every writer of that data, not just the one you were touching.
- Redis `keyPrefix` client option (e.g. `ecom:` / `ecom:test:`) gives free namespace isolation between dev and test without a second Redis instance or database — same pattern already used for Meilisearch index suffixes and the Mongo test database name.
- A Redis `SET ... NX EX` lock used to guard a scheduled job must be released (`DEL`) right after the job finishes, not left to expire on its own — otherwise the *same* instance's own next tick is blocked by its own previous lock until the TTL runs out, which can make a "poll every 2 seconds" job effectively only run every `TTL` seconds. Caught by a genuinely flaky test (BRD 23's outbox-relay test failed only when it was the first test in a file, right after a previous test file's app had grabbed the lock near the end of its life and closed without releasing it) — not by reading the code. TTL should be sized as a crash-safety net only (so a replica that dies mid-job doesn't wedge the lock forever), with an explicit release in a `finally` as the normal path.
- NestJS's `@Sse()` handler: the framework resolves the handler's returned `Observable` and starts committing the 200 response and SSE headers *before* it actually subscribes to (and thereby runs) that Observable. An `await` inside an async `@Sse()` method that should reject with a 4xx (e.g. an ownership check) fires too late — by the time it throws, the client already has a 200 stream, and the error becomes an in-band `{type:'error'}` SSE message instead of a real HTTP error. Any check that must produce a genuine non-200 status for an SSE route has to run in a `CanActivate` guard instead, which executes before any of that.
- NestJS lifecycle hooks: `onModuleInit` across different providers is not guaranteed to run in dependency order just because one constructor-injects another — two providers with no injection relationship between them (e.g. a connection service and an unrelated consumer that both happen to need that connection ready) can have their `onModuleInit`s fire in either order. `onApplicationBootstrap` is the actual guarantee: Nest runs *every* provider's `onModuleInit` first, then calls `onApplicationBootstrap` on any of them — so a provider that must start work only after some other provider's `onModuleInit` has fully finished belongs in `onApplicationBootstrap`, not `onModuleInit`.
- A Prisma `Json` column's `@updatedAt`-style auto-managed timestamp sibling (or `@updatedAt` itself) can't be backdated through an ordinary `.update()` call — Prisma always sets it to `now()`. A test that needs to simulate "this row sat untouched for N minutes" has to use a raw SQL update (`$executeRawUnsafe`/`$executeRaw`) instead.
- `spawnSync(cmd, args, { stdio: 'inherit', input: buffer })` silently drops `input` — Node requires `stdio[0]` to be `'pipe'` for the `input` option to actually reach the child's stdin; with `'inherit'` the child just sees an empty stdin (surfaced here as `pg_restore: error: input file is too short`, not an obvious "your input option was ignored" message). Set `stdio: ['pipe', 'inherit', 'inherit']` whenever a spawned call also passes `input`.
- Two `libs/storefront/catalog` tests (`catalog-pages.spec.ts`'s accessibility scan, `reviews-flow.spec.ts`'s "signed out, then not a buyer" case) intermittently time out at their 5000ms/30000ms limits on this machine — confirmed pre-existing and environment-specific, not caused by any particular change: reproduces even running that one project alone with every Docker container (including all of BRD 24's new observability ones) stopped. `storefront-account`'s equivalent flake did pass cleanly in isolation, so this is closer to "some tests are genuinely borderline on this hardware" than "the suite is now broken" — worth raising the timeout on the accessibility scan specifically (axe-core is real, non-trivial work) rather than chasing it as a regression.
