# Architecture

## 1. Target system (context)
Modular monolith backend first (Node.js/NestJS), later extracted into services. Clients: Angular apps. Data: PostgreSQL (transactions), MongoDB (catalog), Redis (cache/session/locks), RabbitMQ (events/jobs), Meilisearch (search), MinIO/S3 (media). Payments: Razorpay. Runs on Docker Compose, then local Kubernetes, later cloud. Full detail comes with the backend phase; the frontend must not depend on any of it directly.

## 2. Frontend architecture

### 2.1 Layers
```
Page (route component)          -> composes features, no business logic
  Feature components + Store    -> state, orchestration, view models
    Data-access (API client)    -> the ONLY place that knows about HTTP / mock
      Adapter: Mock | HTTP      -> chosen by config
Shared UI (dumb) | Util | Models
```
Rules: data flows down via signal inputs, events flow up via outputs. Stores expose read-only signals plus methods. Components never call `HttpClient` directly.

### 2.2 Mock-data strategy (key decision)
Backend does not exist yet, so we build against **contracts**:
- Every backend capability is an abstract class / injection token in `libs/shared/data-access` (e.g. `CatalogApi`, `CartApi`, `AuthApi`, `OrderApi`, `SearchApi`, `PaymentApi`).
- Two adapters per API: `Mock*Api` (reads JSON from `libs/shared/data-access/src/mock/data/`, in-memory mutable state, simulated latency 150-500 ms and occasional configurable errors) and `Http*Api` (real, added when backend exists).
- Selection is by provider config from environment (`useMocks: true`), so switching to the real backend is a config change, not a code change.
- DTO shapes in `models/` are designed as the future API contract (REST + GraphQL-friendly). Any change to them updates the module BRD.
- Mock adapters mimic real behaviour: pagination, filtering, sorting, facets, stock checks, validation errors, auth tokens (fake JWT), idempotency keys. Search mock uses a simple in-memory index shaped like Meilisearch responses (hits, facetDistribution, estimatedTotalHits) so the swap is cheap.
- Mock data volume: enough to test UX at scale (about 200+ products across fashion, electronics, grocery, home; 30+ categories; varied variants and attributes; images from placeholder services or local assets). Fixtures are generated by a script (`tools/generate-mock-data`) with a fixed seed, so they are reproducible.
- Persistence for mock state: `localStorage` (cart, wishlist, session, orders) so refresh keeps state. Clearly namespaced (`ecom.mock.*`).

### 2.3 State management
| State type | Where |
|---|---|
| Local UI (open/closed, form) | component signals |
| Feature state (listing filters, PDP variant) | feature store (SignalStore) |
| App-wide (auth, cart, wishlist, theme, toasts) | root-provided stores in `shared` or app-shell libs |
| Server cache | store-level caching with TTL + explicit invalidation (mirrors the backend Redis approach) |
| URL state (filters, sort, page, query) | Router query params are the source of truth for listing/search, so pages are shareable and SSR-friendly |

### 2.4 Routing and rendering
- Storefront uses SSR + hydration (SEO for product/category/home). Admin and seller are client-rendered.
- Public routes: `/`, `/c/:categorySlug`, `/p/:productSlug`, `/search`, `/cart`, `/checkout`, `/account/*`, `/wishlist`, `/orders/*`, CMS pages.
- Functional guards: `authGuard`, `roleGuard`. Resolvers only for data needed before render (PDP for SEO meta).
- Slug-based URLs; canonical + meta tags set through a `SeoService`.
- Anything using `window`, `localStorage`, etc. must go through platform-safe abstractions (`isPlatformBrowser`, injected `STORAGE` token) for SSR.

### 2.5 Cross-cutting
- HTTP interceptors (used by the HTTP adapter and by mock-aware infra): auth token, correlation id (`x-request-id`), error mapping, retry with backoff for idempotent GETs, loading indicator.
- `ErrorHandler` global + `ToastService`.
- `FeatureFlagService` (static config for now; remote later) to keep P2/P3 features hidden.
- `AnalyticsService` interface with a console/no-op adapter (real provider later).
- Config: typed `AppConfig` token from environment files; no secrets in the frontend.

### 2.6 GraphQL vs REST on the frontend
Data-access interfaces are protocol-agnostic. Storefront reads (catalog, home, PDP) are expected to move to GraphQL later; transactional flows (checkout, payment, auth) to REST. This lives entirely inside `Http*Api` adapters, so components are unaffected.

## 3. Module map (frontend)
| Module | Storefront | Admin |
|---|---|---|
| auth | login/register/reset | admin login, roles |
| catalog | home, listing, PDP | product/category CRUD, media |
| search | search page, autocomplete | (later) synonyms/analytics |
| cart | cart drawer + page | n/a |
| checkout | address, shipping, payment (Razorpay mock) | n/a |
| orders | history, detail, tracking | order management |
| account | profile, addresses, wishlist | users |
| promotions | coupons, deals | coupon/banner management |
| inventory | stock badges | stock management |
| cms | static pages, banners | content editor |

Suggested build order (each starts with its BRD): shell + design system -> catalog (home/listing/PDP) -> search -> cart -> auth + account -> checkout + orders -> wishlist/reviews -> admin app.

## 4. Future-proofing hooks (do not build yet, just do not block)
Multi-currency (money type carries currency), i18n (no string concatenation), B2B (customer groups and price tiers as optional fields on the price model), marketplace (`sellerId` optional on product/order line), real-time (store methods accept pushed updates).
